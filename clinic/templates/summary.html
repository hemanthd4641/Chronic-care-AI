LLM/RAG Integration Guide (Chatbot)
Add one of the following backends and wire it in chatbot/views.py:
Option A: LangChain + Ollama (local)
  1. Install: pip install langchain langchain-community ollama
  2. Run Ollama and pull a model: ollama pull llama3.1
  3. Ingest docs to vector store (e.g., FAISS) and save index.
  4. In chatbot/views.py, load retriever and call LC chain → response.
Pros: private, offline. Cons: needs GPU/CPU resources.
Option B: LangChain + Hugging Face Inference
  1. Install: pip install langchain langchain-community huggingface-hub
  2. Set HUGGINGFACEHUB_API_TOKEN in environment.
  3. Use HF text-generation endpoint via LangChain LLM wrapper.
  4. Pair with a retriever (FAISS/Chroma) to enable RAG.
Pros: quick setup. Cons: internet, token costs/rate limits.
Minimal RAG Steps
  1. Chunk project PDFs/HTML → embeddings (e.g., all-MiniLM-L6-v2)
  2. Store in FAISS/Chroma (persist to media/vectorstore/)
  3. Build retriever: top-k=4, mmr for diversity
  4. Prompt: context + user question → LLM → answer with sources
Django Wiring
  1. Add a POST endpoint in chatbot/views.py that accepts message
  2. Call chain (retriever → llm) and return JSON
  3. Update chatbot/templates/chatbot.html to fetch this endpoint
  4. Cache embeddings and chain objects on module load
Tip: Start with Option A locally. When stable, switch to Option B for cloud scaling.

  5. Core models: Appointment, PredictionHistory, PrivateMessage, health logs/reminders, store items/cart.

  7. Messaging: Private inbox/sent for users; doctors get a patient-wise overview with unread counts.
  8. Prediction (ML): Typed forms coerce inputs to numeric; models loaded with joblib from ml_train/ml_models; results saved to PredictionHistory and visualized.
  9. Health Tracker: Daily logs and medication reminders; dashboard charts show trends; cross-links with prediction history.
  10. Data & ORM: Uses SQLite. Typical ORM patterns: .filter(), .count(), .annotate(), .get_or_create(). JSON fields for flexible payloads.
  11. Error handling: Friendly template messages; descriptive prediction errors; robust URL namespacing; graceful fallbacks when assignments are missing.
  12. Performance & UX: Compact cards, scrollable tables, fixed-height charts, debounced client search; AJAX for non-blocking updates.

Closing line: "It’s a cohesive, role-aware platform with clean Django separation (models-views-templates), pragmatic ML integration, and optional LLM/RAG augmentation for a smarter chatbot."
Architecture & How It Works

The frontend is rendered with Django templates and Bootstrap 5 for responsive UI. A shared layout in templates/base.html and a global templates/navbar.html define consistent structure and navigation. Pages use small amounts of JavaScript for search filtering, form enhancements, Chart.js visualizations, and AJAX calls where instant updates improve UX.

The backend follows Django’s MTV pattern. URL dispatch in hostel_management/urls.py delegates to each app’s urls.py. Views are thin, focusing on input validation, ORM queries, and passing data to templates. Models capture core entities like users, doctor–patient relationships, appointments, prediction history, messages, health logs, and store items. SQLite is used in development for fast iteration.

Data flows are role-aware. When a patient books an appointment, the system first checks for an assigned doctor via DoctorPatientRelationship. If none exists, the booking form falls back to listing doctors (superusers). Created appointments appear immediately in the doctor’s view, where status can be changed via an AJAX endpoint, refreshing both the card list and summary counts without a full page reload.

Predictions use pre-trained scikit-learn models stored under ml_train/ml_models. Forms convert categorical inputs to numeric using TypedChoiceField so the feature vector aligns with the model’s expectations. Each successful prediction is saved to PredictionHistory, which directly powers history tables and Chart.js charts. Error handling is designed to be human-readable, guiding users to correct inputs or alerting them when a model file is missing.

Messaging combines a patient’s private inbox/sent view with a doctor overview that aggregates messages by patient and highlights unread items. This lets doctors triage quickly, while patients get a standard threaded experience. Simple read flags support badge counts and subtle UI emphasis.

The health tracker records daily measurements and medication reminders. Its dashboard renders recent entries and trend charts, and cross-links with prediction history for context. This pairing helps users see how lifestyle or adherence might correlate with model outcomes.

The medical store demonstrates catalogue and cart flows. Items can be added from the listing; the cart page manages quantities and totals. The navbar “Payments” shortcut points to the cart by design for a direct purchase workflow.

For a smarter assistant, the chatbot can be backed by LLM/RAG. Locally, LangChain with Ollama provides privacy and low-latency iteration; in the cloud, LangChain with Hugging Face Inference offers quick scale. Documents are chunked and embedded into a vector store (e.g., FAISS/Chroma). A retriever feeds the LLM a compact context window, producing grounded answers with cited sources. A thin Django POST endpoint connects the web UI to the chain and returns JSON.

End-to-End Workflow (Patient & Doctor)

A typical session starts with authentication. After login, users land on a role-aware dashboard. Patients primarily interact with bookings, predictions, health tracking, messaging and the store. Doctors focus on managing their assigned patients, triaging messages, and confirming/cancelling appointments.

Patient Journey
  1. Login → Dashboard shows shortcuts and stats tailored to the patient.
  2. Book appointment → If assigned doctor exists, it’s preselected; otherwise, choose from available doctors.
  3. Receive confirmation → Track status in “My Appointments”.
  4. Use Predictor → Submit disease form, view risk and confidence, result saved to history.
  5. Review History/Compare → Charts update from PredictionHistory via /predict/chart-data/.
  6. Log health data → Daily metrics and medications populate health dashboard trends.
  7. Send/receive messages → Private inbox/sent supports quick questions to the doctor.
  8. Browse store → Add medicines to cart, manage quantities, proceed to checkout flow (demo/cart).
Doctor Journey
  1. Login as superuser → Dashboard shows doctor-specific stats (today’s appointments, pending, confirmed).
  2. Manage Assignments → Link/unlink patients via DoctorPatientRelationship.
  3. Appointments → Filtered to this doctor; update status via AJAX for instant feedback.
  4. Messages overview → Patient-wise aggregation highlights unread threads for quick triage.
  5. Profile/store access → Standard user features, plus administrative context when needed.
Data Lifecycle & Cross-App Interactions
  • Assignments → Bookings: Active assignment constrains doctor selection in booking; fallback lists all doctors.
  • Bookings → Doctor Dashboard: Newly created appointments appear immediately; status updates recalc dashboard counts.
  • Predictions → Charts: Each prediction writes to PredictionHistory, powering history tables and compare charts.
  • Health Logs ↔ Predictions: Cross-links let users correlate lifestyle logs with prediction outcomes.
  • Messaging: Private messages update unread counters; doctor view aggregates by patient for prioritization.
  • Store: Medicines and cart entries demonstrate transactional flows and UI feedback loops.
Operational Considerations
  • Validation & Errors: Forms validate types; prediction errors are human-readable; missing model files warned.
  • Permissions: @login_required on protected views; doctor-only sections guard by is_superuser.
  • Performance: Compact UI, limited chart heights, client-side filtering, and AJAX minimize reloads.
  • Extensibility: LLM/RAG chatbot can be plugged via LangChain retriever + LLM; vector store persisted.
ML Training, Charts, Roles & Tech Stack
How Models Were Trained
  • Datasets in ml_train/data/ (heart, diabetes, hypertension, kidney).
  • Training scripts: ml_train/train_*.py load CSVs with pandas, split sets.
  • Preprocessing: numeric casting, basic scaling when needed.
  • Algorithm: RandomForestClassifier (robust defaults, low tuning burden).
  • Export: joblib.dump(model, ml_train/ml_models/*.joblib).
At runtime, views load joblib models, map form inputs to feature order, predict, and save to PredictionHistory.
How Charts/VBars Are Plotted
  • Server endpoint /predict/chart-data/ returns JSON aggregates from PredictionHistory.
  • Frontend uses Chart.js to render bar/line charts with fixed heights for compact UI.
  • Legends moved to bottom; containers scroll when needed; tables set max-height.
  • “Compare” and “History” read the same data source for consistency.
This separates data concerns (JSON) from presentation (Chart.js), simplifying maintenance.
Doctor/Patient Separation (No Extra Components)
  • Single user model: doctors are is_superuser=True; patients are regular users.
  • Role-aware navbar toggles links; views guarded with @login_required and request.user.is_superuser.
  • Doctor–patient link via DoctorPatientRelationship drives booking defaults and doctor views.
  • Templates reuse the same base; conditional blocks adjust what each role sees.
This avoids separate auth apps and keeps the codebase lean.
Tech Stack Map (What For What)

FAQ (Short & Clear)
  • Why can’t I run the server from the root folder? Run it from Chronic_care_AI/hostel_management where manage.py lives.
  • I don’t see my doctor in the booking form. If no assignment exists, the form lists all doctors (superusers).
  • Predictions fail or look wrong. Forms coerce to numbers; ensure fields are valid. Models are in ml_train/ml_models.
  • Charts are too tall. Pages use fixed heights; scroll the container to see more.
  • How do I export the summary? Open /summary/ and click the Print button → Save as PDF.
Glossary (Plain English)
  • Appointment Status: Pending/Confirmed/Cancelled state set by the doctor.
  • PredictionHistory: Table that stores every prediction result and confidence.
  • DoctorPatientRelationship: Links one patient to their primary doctor.
  • RAG (Retrieval-Augmented Generation): LLM answers using your documents as context.
  • Vector Store: Searchable index of text chunks represented as embeddings.
Troubleshooting (Common Issues)
  • NoReverseMatch: Check the {% templatetag openblock %} url {% templatetag closeblock %} names match the app’s namespaced URLs.
  • TemplateSyntaxError: Remove unknown template tags or ensure the tag library is registered.
  • Staticfiles W004: Create the missing static/ directory or fix STATICFILES_DIRS.
  • Model file not found: Ensure ml_train/ml_models/*.joblib exist; retrain if needed.
  • Wrong working directory: Run all Django commands in Chronic_care_AI/hostel_management.
